## Comandos

```bash
npm install                 # Node >=20, npm 10 (o package-lock.json é a fonte da verdade; o CI usa `npm ci`)
npm run dev                 # next dev (Turbopack), http://localhost:3000
npm run lint                # eslint
npm run typecheck           # tsc --noEmit
npm test                    # vitest run (todos os src/**/*.test.{ts,tsx})
npx vitest run src/lib/whatsapp/send-message.test.ts   # um único arquivo
npx vitest run -t "parte do nome do teste"             # um único teste pelo nome
npm run test:watch
npm run format              # prettier --write . (o CONTRIBUTING pede typecheck + format antes de um PR)
npm run build               # next build --webpack
```

- O CI (`.github/workflows/ci.yml`) executa lint → typecheck → test → build, com valores fictícios de `NEXT_PUBLIC_SUPABASE_*`, `ENCRYPTION_KEY` e `META_APP_SECRET`. O `vitest.config.ts` injeta os mesmos segredos fictícios, porque `lib/whatsapp/encryption.ts` e `webhook-signature.ts` os leem no carregamento do módulo. Mantenha os valores sincronizados se alterar algum deles.
- **Os builds de produção usam webpack, não Turbopack** (`--webpack`): os workers de PostCSS do Turbopack travam no container de build da Hostinger. Por isso o `next.config.ts` define o alias `@app-messages` duas vezes (Turbopack e webpack); altere os dois.
- Copie `.env.local.example` para `.env.local`. Obrigatórios: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `ENCRYPTION_KEY` (64 hex, AES-256-GCM; rotacioná-la deixa órfãos todos os tokens de WhatsApp armazenados), `META_APP_SECRET` (aceita lista separada por vírgulas para vários apps da Meta).

## Arquitetura

Next.js App Router (Next 16, React 19, Tailwind v4, shadcn + `@base-ui/react`) sobre um projeto **Supabase** hospedado (Postgres + Auth + Storage + Realtime). Não há ORM nem backend separado: os route handlers em `src/app/api` falam direto com o Supabase. **O Next 16 difere das versões anteriores; siga o AGENTS.md e leia `node_modules/next/dist/docs/` antes de usar APIs do Next.**

### Multi-tenancy e autenticação
- Toda tabela é isolada por `account_id` e protegida por RLS. Os usuários pertencem a uma conta com um papel (`owner > admin > agent > viewer`, veja `src/lib/auth/roles.ts`).
- As rotas de API do dashboard chamam `requireRole(...)` de `src/lib/auth/account.ts`; ela retorna `{ supabase, userId, accountId, role }` usando o cliente SSR vinculado ao cookie (`lib/supabase/server.ts`, o RLS se aplica). Converta os erros lançados com `toErrorResponse`.
- O trabalho de segundo plano no servidor (webhooks, motores de automação/fluxo, autenticação por chave da API pública) usa o cliente **service-role** (`SUPABASE_SERVICE_ROLE_KEY`, ignora o RLS), via `lib/flows/admin-client.ts` / `lib/automations/admin-client.ts`. Nesses casos, sempre filtre por `account_id` você mesmo.
- O `src/middleware.ts` renova a sessão do Supabase e redireciona usuários não autenticados. **Toda nova rota de nível superior em `src/app/(dashboard)/` deve ser adicionada a `protectedPaths`** (o `middleware.test.ts` exige isso). `/api/whatsapp/*` retorna 401 sem sessão, a menos que o caminho contenha `/webhook`; tudo o que precisa ser chamado sem sessão (webhooks, cron, backfill) deve ficar fora do prefixo protegido por sessão, como foi feito com `api/cron/contact-photos`.
- A API REST pública `/api/v1` (`src/app/api/v1`, `lib/api/v1`, `lib/api-keys`) autentica com chaves de API com hash e escopo, em vez de sessões. Documentação: `docs/public-api.md`. O `mcp-server/` é um pacote npm separado que encapsula essa API (tem `package.json` próprio e não faz parte do build da raiz).

### WhatsApp: dois provedores atrás de uma única interface
- Os provedores são a **Meta Cloud API** (`lib/whatsapp/meta-api.ts`) e o **WAHA** (`lib/whatsapp/waha-api.ts`). Em vez de um switch de provedor por toda parte, uma conta WAHA se codifica nos mesmos dois valores que os chamadores da Meta já passam: `phoneNumberId = "waha:<account_id>"` e `accessToken = JSON {u,k,s}`; os helpers de envio de `meta-api.ts` delegam ao WAHA quando `isWahaTarget()`. Mantenha novos caminhos de envio passando por esses helpers.
- Entrada: a Meta envia para `api/whatsapp/webhook` (verificação HMAC com `META_APP_SECRET`), o WAHA para `api/whatsapp/waha/webhook`. Ambos alimentam `lib/whatsapp/inbound-processor.ts`, que resolve a identidade do remetente (`wa-identity.ts`: existem remetentes com username e sem telefone, e ids `@lid` do WAHA), deduplica/cria contatos e conversas, armazena mensagens e então distribui para `resumeAwaitingReply` / `runAutomationsForTrigger` (automações), `dispatchInboundToFlows` (fluxos), `dispatchInboundToAiReply` (resposta automática por IA) e webhooks de saída (`lib/webhooks`).
- Saída: `lib/whatsapp/send-message.ts` é o núcleo único usado tanto por `/api/whatsapp/send` quanto por `/api/v1/messages`. Ele lança `SendMessageError`; os chamadores o convertem para o formato de resposta próprio. Os tokens são armazenados criptografados (`encryption.ts`).

#### Comportamentos do WAHA (engine NOWEB) fáceis de errar
- O webhook da sessão assina `message`, `message.any`, `message.ack`, `message.reaction`, `session.status` e `engine.event` (definido por `wahaEnsureSession`; uma sessão ativa deve ser atualizada com `PUT /api/sessions/default` quando essa lista mudar).
- **Mensagens que enviamos de outros dispositivos** (celular, WhatsApp Web) só chegam em `message.any` com `fromMe=true`. `message` é apenas de entrada, então cada tipo de evento trata exatamente uma direção (`translateMessage`). O NOWEB deixa `to` vazio nelas e coloca o id do chat em `from`; o telefone vem de `_data.key.remoteJidAlt` em chats `@lid`. São armazenadas como mensagens `agent` (`storeMirroredOutbound`), sem incremento de não lidas, fluxos, automações nem IA.
- **Eco dos envios do CRM**: as mensagens enviadas pelo CRM são armazenadas com o id simples do WAHA (`3EB0…`), enquanto ecos/acks trazem `true_<chat>_3EB0…` (a parte do chat pode variar, `@c.us` vs `@lid`). Sempre compare pelo id final: `message_id.eq.<id>,message_id.like.*_<id>`. Pular isso duplica toda mensagem enviada pelo CRM e congela os ticks de entrega em "enviado".
- **Lida em outro dispositivo**: o NOWEB não emite `message.ack` para isso. O CRM escuta o `engine.event` bruto `messages.update` (`key.fromMe=false`, `update.status >= 4`) e zera o contador de não lidas (`markInboundRead`).
- Não registre em log payloads brutos de `engine.event`: `creds.update` carrega chaves privadas.
- Os nomes dos contatos vêm do `pushName` do WhatsApp do remetente; nas nossas próprias mensagens ele é o NOSSO nome e não deve ser usado.

#### Números de telefone
Armazenados exatamente como o WAHA/WhatsApp os informa (muitos celulares brasileiros antigos não têm o nono dígito). As telas os exibem via `formatPhoneDisplay` / `displayContactHandle` (`+55 (xx) 9xxxx-xxxx`, fixo `+55 (xx) xxxx-xxxx`); isso é **somente para exibição**, nunca grave a forma mascarada de volta. A correspondência com sistemas externos usa `brazilianCanonical` (sempre com o nono dígito).

### Integração ssOtica (API Consultiva, somente leitura)
- Credenciais: Configurações → ssOtica (`ssotica_config`: chave de API criptografada, CNPJ e `store_hash` opcional, o código curto da loja nas URLs web do ssOtica). Salvar exige um "Testar chave" aprovado; o servidor repete o teste. Cliente: `lib/ssotica/client.ts` (`GET https://app.ssotica.com.br/api/v1`, Bearer key + `cnpj`; **nunca chame `POST /login`**, isso invalida a chave do usuário).
- A API **não tem busca por telefone** e permite 60 chamadas/min por loja, então `lib/ssotica/sync.ts` espelha os clientes em `ssotica_customers` (telefones canônicos, último número/data/situação/etapa/flag de vendida da OS, data do último recibo, número/data/valor da última venda e o vendedor — primeiro nome do `funcionario` da última venda, com fallback para o da última OS; migration 053). O cron `GET /api/cron/ssotica-sync` (a cada 10 min, mesmo `x-cron-secret`) executa uma passada com orçamento: backfill de clientes → 3 anos de vendas → OS em janelas de 180 dias (várias execuções), depois incremental nos últimos dias. O estado fica em `ssotica_sync_state`; `phase='live'` significa que o índice é confiável. Para reler um conjunto de dados após adicionar colunas, volte a fase (`phase='os'`, `cursor_date=null`) e execute o cron.
- Lista de conversas: `POST /api/ssotica/customers` (em lote, `useSsoticaStatuses`) alimenta uma bolinha azul/vermelha ao lado da bolinha de status de cada linha; nada é exibido até `phase='live'`, para que ninguém seja chamado de "novo" por engano.
- UI: `GET /api/ssotica/customer?phone=` responde `customer | new | unavailable` a partir do índice; selos "Cliente ssOtica" (azul) / "Cliente Novo" (vermelho) no cabeçalho do chat, um selo amarelo de vendedor ao lado deles (somente quando há vendedor vinculado) e a lista de detalhes centralizada no painel do contato (`components/inbox/ssotica-badges.tsx`: nome, nº da O.S., data da O.S. com dias desde então, situação, etapa, venda, valor, data). A etapa ("Etapa da O.S.") só é mantida/exibida para uma OS vendida e não cancelada/perdida. O número e o valor da venda levam a `…/movimentacao/vendas/<store_hash>/listar?nsa_venda_Venda=<n>`; a API **não** retorna código para páginas de OS nem imagens de receita, então esses ficam como texto simples.

### Convenções da UI do inbox
- Toda conversa mostra um `ChannelBadge` (`components/inbox/channel-badge.tsx`: WhatsApp verde, Instagram rosa; apenas ícone na lista, pílula completa no cabeçalho da conversa). A lista tem um filtro **Origem** (todos / WhatsApp / Instagram) ao lado de Status e Tags, baseado em `conversation.channel ?? 'whatsapp'`.
- A lista do inbox filtra `last_message_at IS NOT NULL` e aplica `hasInboxMessage`, para não exibir conversas órfãs sem mensagens persistidas.
- A lista do inbox sanitiza nomes com `cleanContactName`, mostra telefone formatado quando não há nome e traduz os marcadores `[image]`/`[audio]` para Foto/Áudio. O balão de texto usa `LinkPreview` e `/api/link-preview` para gerar thumb de links com proteção SSRF.
- Instagram: `lib/instagram/inbound.ts` espelha anexos recebidos no bucket `chat-media`; `downloadInstagramMedia` repete a requisição com `Authorization: Bearer <token>` para CDNs que exigem autenticação.
- Painel do contato: clique duplo no nome para renomear (grava `contacts.name` pelo cliente RLS); o **+** ao lado de Tags abre um popup para adicionar/remover tags via `lib/contacts/tag-api.ts` (para que as automações `tag_added` continuem disparando).
- A ordem da barra de Configurações = a ordem de `SETTINGS_SECTIONS` em `components/settings/settings-sections.ts` (o Instagram fica logo abaixo do WhatsApp). Novas rotas do dashboard também precisam de `protectedPaths` em `middleware.ts`; `/avisos` (menu "Avisos") é uma página provisória.

### DMs do Instagram (`lib/instagram`, migration 054)
- Canal = `conversations.channel` (`whatsapp` padrão | `instagram`). Um contato do Instagram tem `contacts.ig_user_id` (IGSID), `phone = ''` e seu @username em `wa_username`. A conexão por conta fica em `instagram_config` (token criptografado com AES-GCM, 60 dias).
- **Instagram API com Instagram Login**, não Facebook Login. Variáveis de ambiente (de toda a implantação): `INSTAGRAM_APP_ID`, `INSTAGRAM_APP_SECRET`, `INSTAGRAM_VERIFY_TOKEN` (handshake GET do webhook), mais `NEXT_PUBLIC_SITE_URL` (redirect OAuth `/api/instagram/oauth/callback`, webhook `/api/instagram/webhook`). As assinaturas do webhook são aceitas com `INSTAGRAM_APP_SECRET` ou `META_APP_SECRET` (`lib/instagram/security.ts`). Configurações → Instagram mostra as URLs a colar no app da Meta.
- Entrada (`inbound.ts`, parsing do payload no `events.ts` puro): idempotente em `(conversation_id, message_id)`. Os **ecos** (`is_echo`: enviados pelo CRM, pelo app do Instagram ou por outra ferramenta) chegam no mesmo webhook; são gravados via upsert como linhas `agent`, de modo que o envio do próprio CRM e seu eco colapsam em uma única linha — mantenha os dois escritores em `upsert … ignoreDuplicates`. Os anexos são espelhados (`mirrorInboundMedia`, os links da CDN expiram). Uma conversa **nova** é inserida (INSERT) já com `last_message_text`, `last_message_at` e `unread_count` (e pula o RPC de incremento): o inbox hidrata a conversa assim que o INSERT chega via realtime, e um UPDATE de seguimento alguns ms depois poderia se perder, deixando "nenhuma mensagem ainda" na lista.
- Saída: `send-message.ts` entrega `channel='instagram'` a `lib/instagram/send.ts` (texto ou um anexo de mídia, apenas respostas). Janela: 24 h livres, até 7 dias com a tag `HUMAN_AGENT` (`sendWindow`), depois bloqueado; o timer da conversa usa 168 h para o Instagram. Sem templates, botões, notas de voz, automações, fluxos nem IA no Instagram (por design na v1).
- `GET /api/cron/instagram-refresh` (diário, `x-cron-secret`) renova tokens que expiram em até 15 dias; um irrecuperável muda o `status` para `disconnected`. Não é necessário App Review enquanto o app atende apenas a conta do próprio dono (Standard Access): o perfil do Instagram só precisa ser *Instagram Tester* do app e ter "Permitir acesso às mensagens" ativado. Também é possível conectar uma conta sem a tela de OAuth, salvando um token gerado no dashboard (criptografado com `ENCRYPTION_KEY`) em `instagram_config`, após `POST /me/subscribed_apps`.

### Motores e cron
- `lib/automations/engine.ts` (gatilho → condições → passos, com passos de Espera) e `lib/flows/engine.ts` (grafo de nós armazenado no banco, percorrido por contato, suspendendo em nós de entrada; idempotente por id de mensagem da Meta, atualizações otimistas de `current_node_key`, uma execução ativa por contato via índice único parcial) enviam ambos por seu próprio `meta-send.ts`.
- Os passos de Espera e os timeouts de fluxo são drenados por `GET /api/automations/cron` e `/api/flows/cron`, protegidos pelo header `x-cron-secret` = `AUTOMATION_CRON_SECRET`. Nada os agenda por você: em produção, o cron do host os chama a cada minuto.
- Assistente de IA (`lib/ai`): traga sua própria chave OpenAI/Anthropic/compatível com OpenAI por conta (armazenada criptografada); base de conhecimento com full-text do Postgres e pgvector opcional. Em **Agentes de IA**, `IA Sandbox Cliente` testa conversas da Maria; `IA Sandbox Receitas` usa o modelo/prompt visual configurado com upload efêmero em memória, sem Storage, mensagens ou tabela de leitura. O bloco **Assistente de resposta do chat** controla o modelo/prompt da função “Redigir uma resposta com IA”; o interruptor no cabeçalho permite ativar/desativar a IA por conversa e a opção de pausa após mensagem manual respeita `ai_configs.disable_ai_on_agent_message`.
- O interruptor por conversa é exibido quando a IA está configurada e ativa, mesmo com a resposta automática global desligada; nesse caso fica desabilitado até a ativação global.
- Correios: o painel de Logística aceita credenciais tradicionais do Meu Correios ou chave CWS `cws-...`. A chave CWS é armazenada criptografada e usada diretamente como Bearer; não deve ser enviada ao endpoint Basic de usuário/senha.
- A transcrição de áudio pode ser automática na entrada quando `ai_configs.transcription_enabled` está ativo e também pode ser solicitada manualmente para mensagens já armazenadas. Usa somente provedor OpenAI / compatível com OpenAI, com modelo padrão `whisper-large-v3-turbo` no Groq; o texto é gravado em `messages.content_text`, exibido em itálico e reutilizado pela resposta automática. O atalho manual fica em `components/inbox/audio-transcription.tsx`, a rota é `POST /api/ai/transcribe-message` e a implementação está em `lib/ai/transcribe.ts`.
- A resposta automática de IA tem uma agenda semanal opcional em `ai_configs.auto_reply_schedule`: quando desativada, permanece 24/7; quando ativada, usa exclusivamente o fuso `America/Sao_Paulo` e fica em silêncio fora dos horários válidos. Agendas inválidas falham de forma segura, sem desligar o uso manual da IA. A configuração fica em `components/settings/ai-schedule-editor.tsx`, com validação em `lib/ai/schedule.ts`.
- O assistente padrão Maria (`lib/ai/maria-prompt.ts`) atende em português brasileiro e não pode diagnosticar, recomendar lentes, inventar dados ou confirmar operações não comprovadas. A leitura privada de receitas (`api/ai/prescription-read`, `lib/ai/prescription.ts`) só aceita imagens recebidas, fica visível à equipe da conta, grava resultados em `ai_prescription_reads` com escopo por conta e nunca faz diagnóstico ou recomendação clínica.

### i18n
O idioma da UI é um único locale em tempo de build, `NEXT_PUBLIC_APP_LOCALE` (`en|pt|es|ko`, padrão `en`), carregado de `messages/<locale>.json` pelo alias `@app-messages` (`src/i18n`, next-intl). O código de servidor/lib usa `getT("Namespace.key")` de `lib/i18n/translate`. Novas strings visíveis ao usuário vão nos **quatro** catálogos. Mudar o locale exige novo build.

### Banco de dados
`supabase/migrations/NNN_*.sql` (sequenciais, atualmente até 067). A migration 062 adiciona a agenda semanal e o fuso das respostas automáticas de IA; a 063 adiciona a configuração e os resultados privados da leitura de receitas; a 064 cria o monitoramento de encomendas dos Correios; a 065 armazena as credenciais Meu Correios e o token renovável por conta; a 066 cria a configuração OAuth do Google Business Profile e os campos do agente de respostas de avaliações; a 067 cria o Assistente de resposta do chat e a pausa após mensagem manual. O CI (`migrations.yml`) apenas as valida em um Postgres descartável (`supabase/ci/verify-schema.sql`); **ele nunca as aplica em um projeto real**. Aplique as novas migrations manualmente (SQL editor do Supabase ou `supabase db push`) **antes** de publicar uma imagem que leia as novas colunas. O `supabase/ci/verify-schema.sql` é um único bloco `DO`; adicione as asserções dentro dele.

### Deploy
`output: "standalone"`; o `Dockerfile` é multi-stage e usa `NODE_OPTIONS=--max-old-space-size=1536` durante o build. Os valores `NEXT_PUBLIC_*` são embutidos em tempo de build (build args do Docker / Variables do repositório), então alterá-los exige novo build. A action `publish-image.yml` (`workflow_dispatch` manual) constrói e publica `ghcr.io/<owner>/wacrm:latest`; o servidor então executa `docker compose pull && docker compose up -d`. A imagem `ghcr.io/bruno-hao/wacrm` é pública (o pull não precisa de login); só o workflow publica, com o `GITHUB_TOKEN`, sem PAT. O Compose usa `TZ=America/Sao_Paulo` como padrão operacional, e os segredos apenas de servidor são variáveis de ambiente de runtime, nunca embutidas na imagem. Veja `docs/docker.md`.

Quando o usuário pedir qualquer alteração no sistema, execute o fluxo completo de produção sem pedir novas confirmações entre as etapas: valide e crie o commit, envie-o ao Git remoto, execute e acompanhe até o fim o workflow `publish-image.yml` e, somente se a publicação terminar com sucesso, conecte à VPS por SSH na porta `22022`, execute `docker compose pull && docker compose up -d` (ou `--force-recreate` quando a tag tiver mudado sem recriar o contêiner) em `/root/wacrm` e confirme a saúde do contêiner e a correspondência entre a imagem executada e a publicada. Se uma etapa falhar, pare antes da seguinte e informe o ponto exato da falha. Isso inclui alterações de código, configuração, banco, infraestrutura e documentação operacional.

Após cada alteração que afete comportamento, infraestrutura, versões, migrations ou procedimentos, mantenha sincronizados este `CLAUDE.md`, `AGENTS.md`, `/root/.claude/CLAUDE.md` e `/root/wacrm-handoff/LEIA-PRIMEIRO.md`.
